How the AI works

The honest technical breakdown — what's a real model call, what isn't, and why.

Where the real AI is

Two features make live model calls — both server-side, both Google Gemini 3.6 Flash via the Gemini generateContent API, API key never reaching the browser:

Handover item draftingHR/Manager dashboard's "AI: Draft items" button (Step 1). Reads the employee's real linked self-review + manager-expectations docs and asks Gemini to extract concrete handover items — told explicitly to write "Not specified in docs" rather than invent a stakeholder, status, or project that isn't actually in the text. This is what populates the Handover Validation Dashboard (Step 2) for any real employee, not just the seeded TR-1042 (Alisha) demo data.
Successor Companion chatStep 6. Everything the successor types goes to a real, running LLM, grounded in that transition's live (AI-drafted-then-validated) handover items and captured context Q&A — it is not answering from a script.

Both are drafts, not facts: item-drafting output sits as "pending" until the employee confirms/edits/disputes it (Step 2), and the companion's answers are explicitly sourced so nothing is taken on faith.

The grounding pattern — and what we're not calling it

We deliberately don't call this a "RAG pipeline." Classic RAG retrieves from a large corpus via vector embeddings + similarity search. Our data per transition is small and already structured (a handful of validated handover items and Q&A rows) — so instead of building an embeddings index for a dataset that small, we do structured context injection: pull the transition's rows straight out of SQLite and put them directly in the prompt, with an explicit instruction to answer only from those facts.

  • Retrieval step: a plain SQL query (getFullTransitionState), not a vector search
  • Generation step: Gemini, instructed to decline rather than invent an answer if the facts don't cover the question

This is the right-sized architecture for the data volume involved — not a shortcut dressed up as something bigger.

What's deliberately NOT AI — and why

Everything else in the product is plain code, on purpose:

Doc search & tagging Knowledge pack assembly Successor Q&A fallback Handover item drafting Successor Companion chat

The doc-search feature ("Scan documents for excerpts" — finding relevant excerpts in an employee's linked docs to show alongside context-capture questions) is keyword and tag matching — no model call, and a separate code path from item drafting above even though both read the same documents. The knowledge pack is template assembly over validated data. The companion's fallback path (used if Gemini is unavailable) is keyword-overlap scoring, not a second model.

Why plain code instead of AI everywhere: these steps deal with facts that must be exactly right — what an employee actually validated, what a manager actually approved. Using deterministic matching there means zero hallucination risk on the facts that matter most. Both places we do use a model produce a draft that a human must check, not a final fact: item-drafting output starts as "pending" until the employee confirms/edits/disputes it, and the companion is instructed to say "I don't know" rather than invent an answer the docs don't support.
Handling AI latency & failure honestly

Model calls are slower and less predictable than a database read, so the companion is built to show that, not hide it:

  • While waiting: the chat shows an animated "thinking" indicator in place of the answer bubble — the UI never freezes or looks broken during the ~1-3s Gemini call.
  • If Gemini times out, errors, or the key is misconfigured: the companion automatically falls back to local keyword matching over the same captured facts, and says so explicitly in the answer's source line (e.g. "keyword fallback — AI unavailable") — it never silently pretends the fallback answer came from the model.
  • If Gemini returns nothing usable (e.g. blocked by a safety filter): same honest fallback, same visible labeling.

We scoped this to a clear loading state + a transparent, labeled fallback rather than building full token-by-token streaming (SSE) — the right trade-off for a hackathon timeline, without pretending the non-determinism of an LLM call away.
